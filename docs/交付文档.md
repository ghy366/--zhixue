## 三、架构修复(300 人压测实证)

压测中发现并修复 **全站冻结级并发缺陷**(jstack 实证链):

```
结算事务持配置行锁 → tick 的 synchronized sync() 被卡 → 手握全局 Java 监视器
→ getSystemConfig 被所有接口调用且必须过此监视器 → 300 并发全排队
→ 排队线程经 OSIV 各持数据库连接(池仅10) → 监视器持有者也在等连接
→ 连接池死锁 → 全站接口超时(CPU 0%,10 分钟不可恢复)
```

| 修复 | 内容 | 验证 |
|---|---|---|
| 读路径去同步化 | `getSystemConfig` 直读配置行;时间窗校准交还 30 秒 tick 与管理端显式操作 | 重启后 300 并发查询 1.7s 零异常 |
| 连接池扩容 | Hikari 10 → 30(`application.yml` hikari 节) | 同上 |
| MySQL 连接上限 | 本机 my.ini `max_connections` 20 → 300(**需 MySQL 服务重启生效,已执行**) | SHOW VARIABLES 确认 300 |

**压测关键数据**:300 并发登录 3.2s · 300 并发投分 1.4s 零异常 · 218 笔结算 7.06s · 错峰闸门拦截 50/50 → 放行 50/50 · 全员人均选修 2 门。
